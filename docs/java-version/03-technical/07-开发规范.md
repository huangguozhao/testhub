## 核心原则

> **任何开发必须遵循以下核心原则，违反则必须修复。**

### 原则 1：人负责边界把控与验收，AI 负责执行体力活

**AI 的职责**：
- 根据人类指令编写代码
- 执行重复性机械操作
- 遵循既定规范格式化代码
- 查找并修复指定类型的小问题

**人类的职责**：
- 定义功能范围和验收标准
- 设计模块结构和接口契约
- 审查 AI 生成的代码
- 做最终验收决策

**禁止**：
- 让 AI 自主设计架构
- 让 AI 自主决定业务逻辑
- 让 AI 自主修改未授权的文件

### 原则 2：坚守小步迭代的 MVP 法则

**规则**：

1. **每次只完成一个可验证的小功能切片**
   - 一个接口 + 单元测试
   - 一个 Service 方法 + 测试
   - 一个工具类 + 测试

2. **每完成一个切片，立即执行**：
   ```
   编译 → 测试 → Lint检查 → 提交Git
   ```

3. **禁止行为**：
   - 一次性让 AI 生成大量代码（>500行未经验证）
   - 积累多个未提交的修改
   - 在未验证的情况下继续添加新功能

### 原则 3：人工介入做模块拆分

**要求**：

1. **禁止所有代码放在同一文件中**
   - 单个文件不超过 500 行
   - 单个方法不超过 80 行
   - Controller 不超过 20 个方法
   - Service 不超过 30 个方法

2. **人工规划模块拆分**：
   - 在开始编码前定义类结构
   - 明确每个类的职责
   - 记录在「开发参考」文档的模块设计部分

3. **违反时必须重构**：
   - 发现超大文件立即拆分
   - 发现职责不清的类立即重构

### 原则 4：限制 AI 权限，禁止 AI 自主决策

**给 AI 的指令格式**：

```
请完成 [具体功能]
- 仅修改文件：A.java, B.java
- 不修改文件：C.java, D.java
- 输出要求：[具体格式]
- 验收标准：[具体检查点]
```

**AI 被禁止的行为**：

| 禁止行为 | 说明 |
|----------|------|
| 顺手重构 | 未授权的文件不能修改 |
| 优化代码 | 未授权的优化不能做 |
| 改变业务逻辑 | 只能按指定逻辑实现 |
| 添加依赖 | 未授权不能添加新依赖 |
| 修改配置文件 | 未授权不能修改配置 |
| 提交代码 | 人类负责 Git 操作 |

### 原则 5：死守安全底线

#### 5.1 密钥安全

**绝对禁止**：

```
❌ API密钥硬编码在代码中
❌ API密钥硬编码在配置文件中
❌ API密钥提交到 Git 仓库
❌ API密钥传输到前端
```

**正确做法**：

```yaml
# application.yml - 使用环境变量
spring:
  datasource:
    password: ${DB_PASSWORD}

jwt:
  secret: ${JWT_SECRET}

ai:
  api-key: ${AI_API_KEY}
```

```bash
# 环境变量或启动参数
export DB_PASSWORD=xxx
export JWT_SECRET=xxx
java -jar app.jar --DB_PASSWORD=xxx
```

#### 5.2 前端不存储密钥

```
❌ 禁止在前端代码中存储任何密钥
❌ 禁止在 LocalStorage/SessionStorage 中存储密钥
❌ 禁止将密钥通过 URL 参数传递
```

#### 5.3 服务端必须校验

**输入校验**：

```java
// 禁止信任前端数据，必须校验
@PostMapping
public Result<Void> createUser(@Valid @RequestBody CreateUserRequest request) {
    // @Valid 注解 + 注解校验
    // 业务层再次校验
}
```

**权限校验**：

```java
// 禁止信任前端传输的权限数据
public void updateProject(Long projectId, Long userId) {
    // 1. 验证用户是否登录
    // 2. 验证用户是否有权限操作该项目
    // 3. 禁止相信前端传来的 role/permission 字段
}
```

**禁止**：

```java
// ❌ 错误：相信前端传来的角色
public void updateUser(Long id, String role) {
    user.setRole(role);  // 禁止！前端传来的 role 不可信
}

// ✅ 正确：服务端自己判断角色
public void updateUser(Long id, UpdateUserRequest request) {
    Long currentUserId = getCurrentUserId();
    // 服务端自己判断权限
    if (!hasPermission(currentUserId, id)) {
        throw new UnauthorizedException();
    }
}
```

#### 5.4 SQL 注入防护

```java
// ❌ 禁止：字符串拼接
@Select("SELECT * FROM user WHERE name = '" + name + "'")

// ✅ 正确：参数绑定
@Select("SELECT * FROM user WHERE name = #{name}")
```

#### 5.5 敏感日志脱敏

```java
// 日志中禁止输出敏感信息
log.info("User login: username={}, password=***", username, password);
log.info("API response: data={}", sensitiveData);  // 脱敏处理
```

## 一、代码规范

### 1.1 Java 代码规范

#### 1.1.1 命名规范

**类名命名**

| 类型 | 规范 | 示例 |
|------|------|------|
| 实体类 | `名词`，与表名对应 | `User`, `Project`, `TestCase` |
| Controller | `XxxController` | `UserController`, `TestCaseController` |
| Service 接口 | `XxxService` | `UserService`, `TestCaseService` |
| Service 实现 | `XxxServiceImpl` | `UserServiceImpl`, `TestCaseServiceImpl` |
| Mapper 接口 | `XxxMapper` | `UserMapper`, `TestCaseMapper` |
| DTO 请求 | `XxxRequest` | `LoginRequest`, `CreateProjectRequest` |
| DTO 响应 | `XxxVO` 或 `XxxResponse` | `UserVO`, `LoginResponse` |
| 枚举类 | `XxxEnum` | `ProjectStatusEnum`, `TaskStatusEnum` |
| 异常类 | `XxxException` | `BusinessException`, `UnauthorizedException` |
| 配置类 | `XxxConfig` | `SecurityConfig`, `RedisConfig` |
| 工具类 | `XxxUtils` 或 `XxxHelper` | `JwtUtils`, `DateUtils` |

**方法命名**

| 操作 | 规范 | 示例 |
|------|------|------|
| 查询单个 | `getXxxById` | `getUserById`, `getProjectById` |
| 查询列表 | `listXxx` 或 `getXxxList` | `listUsers`, `getProjectList` |
| 分页查询 | `pageXxx` | `pageUsers`, `pageTestCases` |
| 保存 | `saveXxx` 或 `createXxx` | `saveUser`, `createProject` |
| 更新 | `updateXxx` | `updateUser`, `updateProject` |
| 删除 | `deleteXxx` 或 `removeXxx` | `deleteUser`, `removeProject` |
| 批量操作 | `batchXxx` | `batchSaveUsers`, `batchDeleteUsers` |
| 校验 | `validateXxx` 或 `checkXxx` | `validateUser`, `checkProjectName` |
| 转换 | `convertXxx` 或 `toXxx` | `convertToVO`, `toEntity` |

**变量命名**

| 类型 | 规范 | 示例 |
|------|------|------|
| 普通变量 | 小驼峰，名词 | `userId`, `projectName`, `pageSize` |
| 常量 | 全大写，下划线分隔 | `MAX_PAGE_SIZE`, `DEFAULT_PASSWORD` |
| 布尔变量 | is/has/can 前缀 | `isActive`, `hasPermission`, `canEdit` |
| 集合变量 | 复数名词或 xxxList/xxxMap | `users`, `userList`, `userMap` |
| DTO 变量 | 与 DTO 类名对应 | `loginRequest`, `userVO` |

**包命名**

```
com.testhub
├── config          # 配置类
├── common         # 公共模块
│   ├── result     # 统一响应
│   ├── exception  # 异常处理
│   ├── utils      # 工具类
│   └── constant   # 常量
├── module         # 业务模块
│   ├── user
│   ├── project
│   └── testcase
└── job            # 定时任务
```

**数据库表/字段命名**

| 类型 | 规范 | 示例 |
|------|------|------|
| 表名 | 小写，下划线分隔，前缀表示模块 | `sys_user`, `prj_project`, `tc_test_case` |
| 字段名 | 小写，下划线分隔 | `user_id`, `project_name`, `created_at` |
| 主键 | `id` | `id` |
| 外键 | `{表名}_id` | `user_id`, `project_id` |
| 索引 | `idx_{表名}_{字段}` | `idx_user_username`, `idx_project_status` |
| 唯一索引 | `uk_{表名}_{字段}` | `uk_user_username`, `uk_project_member` |
| 时间戳 | `{动作}_at` 或 `{动作}_time` | `created_at`, `updated_at`, `login_time` |

#### 1.1.2 代码格式

**类结构顺序**

```java
public class UserController {  // 1. 类声明
    
    // 2. 静态属性/常量
    private static final Logger log = LoggerFactory.getLogger(UserController.class);
    private static final int MAX_RETRY_COUNT = 3;
    
    // 3. 实例属性
    @Autowired
    private UserService userService;
    
    // 4. 构造方法
    public UserController(UserService userService) {
        this.userService = userService;
    }
    
    // 5. 公共方法（API接口）
    @GetMapping("/{id}")
    public Result<UserVO> getUserById(@PathVariable Long id) {
        return Result.success(userService.getUserById(id));
    }
    
    // 6. 私有方法
    private void validateUser(User user) {
        // ...
    }
}
```

**方法长度**：单个方法不超过 80 行（推荐不超过 50 行）

**缩进**：4 空格

**大括号**：K&R 风格（换行开括号）

```java
// 正确
if (condition) {
    doSomething();
} else {
    doOther();
}

// 错误
if (condition) {
    doSomething();
}
else {
    doOther();
}
```

**空行使用**

- 类成员之间空 1 行
- 方法之间空 1 行
- 方法内部逻辑分组之间空 1 行

### 1.2 数据库规范

#### 1.2.1 表设计规范

**必须字段**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键，自增 |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 更新时间 |

**建议字段**

| 字段 | 类型 | 说明 |
|------|------|------|
| created_by | BIGINT | 创建人ID |
| is_deleted | TINYINT | 软删除标记（建议使用） |

**字段规范**

- VARCHAR 类型必须指定长度
- TEXT 类型谨慎使用，优先考虑 VARCHAR
- 时间类型统一使用 DATETIME（不区分时区）或 TIMESTAMP（区分时区）
- 金额/精确数值使用 DECIMAL，禁止使用 FLOAT/DOUBLE

#### 1.2.2 索引规范

| 类型 | 使用场景 |
|------|----------|
| 普通索引 | 查询条件字段 |
| 唯一索引 | 唯一约束字段 |
| 联合索引 | 多字段查询，按区分度排序 |

**注意事项**

- 单表索引不超过 5 个
- 避免在频繁更新的字段上建索引
- 避免在大文本字段上建索引
- 使用 EXPLAIN 分析慢查询

### 1.3 Git 规范

#### 1.3.1 分支命名

| 分支类型 | 命名格式 | 示例 |
|----------|----------|------|
| 主分支 | `main` | main |
| 开发分支 | `develop` | develop |
| 功能分支 | `feature/{功能名}` | feature/user-auth, feature/project-module |
| 修复分支 | `fix/{问题描述}` | fix/token-expired |
| 发布分支 | `release/{版本号}` | release/v1.0.0 |

#### 1.3.2 提交信息规范

**格式**：`type: subject`

```bash
# 示例
feat: 添加用户注册接口
fix: 修复Token刷新失败问题
docs: 更新用户模块API文档
style: 格式化代码
refactor: 重构UserService
test: 添加用户服务单元测试
chore: 更新pom.xml依赖
```

**type 类型**

| type | 说明 |
|------|------|
| feat | 新功能 |
| fix | Bug 修复 |
| docs | 文档更新 |
| style | 代码格式（不影响功能） |
| refactor | 重构（不是新功能或修复） |
| test | 测试相关 |
| chore | 构建/工具相关 |
| perf | 性能优化 |

#### 1.3.3 Commit 规范

**每次 Commit 应该**：

1. 只包含一个逻辑变更
2. 有清晰的提交信息
3. 包含相关测试（如有）

**禁止**：

1. 一次性提交大量不相关的修改
2. 提交未编译通过的代码
3. 提交敏感信息（密码、密钥等）

## 三、开发流程规范

### 3.1 功能开发流程

```
┌─────────────────────────────────────────────────────────────────┐
│                        功能开发流程                               │
└─────────────────────────────────────────────────────────────────┘

1. 需求分析
   │
   ├─ 阅读需求文档
   ├─ 确认接口设计
   └─ 确认数据模型

2. 代码开发
   │
   ├─ 创建/修改 Entity
   ├─ 创建/修改 Mapper (XML)
   ├─ 创建/修改 Service
   └─ 创建/修改 Controller

3. 单元测试
   │
   ├─ Service 层测试
   └─ 工具类测试

4. 代码审查
   │
   ├─ 自检清单
   ├─ 同事审查
   └─ 修复问题

5. 提交代码
   │
   ├─ 功能测试
   ├─ 提交到特性分支
   └─ 创建 Pull Request
```

### 3.2 每次修改的规范

#### 3.2.1 修改前准备

**必须确认**：

1. 了解需要修改的功能范围
2. 查看相关代码的依赖关系
3. 确认修改不会影响其他功能
4. 备份相关代码（或使用 Git）

#### 3.2.2 修改时规则

**规则 1：最小修改原则**

每次修改只涉及必要的文件：

```
✅ 正确做法：
- 修改用户头像：只修改 UserService + UserMapper
- 添加新字段：只修改 User Entity + UserMapper

❌ 错误做法：
- 修改用户头像时，同时修改了 Project、TestCase 等无关模块
- 添加字段时，同时重构了其他代码
```

**规则 2：向后兼容**

数据库字段变更需考虑向后兼容：

```sql
-- ✅ 正确：添加可空字段
ALTER TABLE sys_user ADD COLUMN avatar VARCHAR(255);

-- ❌ 错误：直接删除字段
ALTER TABLE sys_user DROP COLUMN avatar;

-- ✅ 正确：重命名字段分两步
-- 第一步：添加新字段
ALTER TABLE sys_user ADD COLUMN nick_name VARCHAR(100);
-- 第二步：迁移数据
UPDATE sys_user SET nick_name = username;
-- 第三步：确认无误后删除旧字段
ALTER TABLE sys_user DROP COLUMN username;
```

**规则 3：不破坏现有功能**

每次修改后必须验证：

1. 编译通过
2. 原有单元测试通过
3. 原有 API 接口正常

#### 3.2.3 修改后检查

**自检清单**：

- [ ] 代码编译通过
- [ ] 单元测试通过
- [ ] 相关 API 接口正常
- [ ] 没有引入新的编译警告
- [ ] 代码格式符合规范
- [ ] 提交信息清晰

### 3.3 代码审查要点

#### 3.3.1 功能审查

- [ ] 功能是否满足需求
- [ ] 边界条件是否处理
- [ ] 异常情况是否处理
- [ ] 返回值是否合理

#### 3.3.2 代码质量审查

- [ ] 没有重复代码
- [ ] 没有过长的方法
- [ ] 命名是否符合规范
- [ ] 注释是否清晰（关键逻辑）
- [ ] 没有硬编码值

#### 3.3.3 安全审查

- [ ] 输入参数是否校验
- [ ] SQL 注入风险（使用参数绑定）
- [ ] 敏感信息是否脱敏
- [ ] 权限校验是否完整

#### 3.3.4 性能审查

- [ ] 数据库查询是否有索引
- [ ] 是否有 N+1 查询问题
- [ ] 大数据量是否分页
- [ ] 是否有不必要的循环

## 四、接口规范

### 4.1 RESTful API 设计

#### 4.1.1 URL 规范

| 操作 | 方法 | URL | 示例 |
|------|------|------|------|
| 查询列表 | GET | /{resource} | GET /api/users |
| 查询单个 | GET | /{resource}/{id} | GET /api/users/1 |
| 创建 | POST | /{resource} | POST /api/users |
| 更新（完整） | PUT | /{resource}/{id} | PUT /api/users/1 |
| 更新（部分） | PATCH | /{resource}/{id} | PATCH /api/users/1 |
| 删除 | DELETE | /{resource}/{id} | DELETE /api/users/1 |
| 关联操作 | POST | /{resource}/{id}/{action} | POST /api/projects/1/members |

#### 4.1.2 请求参数规范

**路径参数**

```java
@GetMapping("/{id}")
public Result<UserVO> getUserById(@PathVariable Long id) {
    // ...
}
```

**查询参数**

```java
@GetMapping
public Result<PageResult<UserVO>> pageUsers(
    @RequestParam(defaultValue = "1") Integer current,
    @RequestParam(defaultValue = "20") Integer size,
    @RequestParam(required = false) String keyword
) {
    // ...
}
```

**请求体**

```java
@PostMapping
public Result<UserVO> createUser(@Valid @RequestBody CreateUserRequest request) {
    // ...
}
```

#### 4.1.3 响应规范

```json
// 成功响应
{
  "code": 200,
  "message": "success",
  "data": { ... },
```

### 4.2 接口版本管理

**当前策略**：不使用 URL 版本号

```
✅ 当前：/api/users/1
❌ 不使用：/api/v1/users/1
```

**版本控制方式**：

1. 小版本：向前兼容的修改（新增字段、新增接口）
2. 大版本：不兼容的修改（需要前端配合）

## 五、安全规范

### 5.1 输入校验

**必须校验**：

1. 必填字段
2. 长度限制
3. 格式校验（邮箱、手机号等）
4. 数值范围
5. 枚举值

**使用校验注解**：

```java
public class CreateUserRequest {
    
    @NotBlank(message = "用户名不能为空")
    @Size(min = 3, max = 50, message = "用户名长度3-50")
    private String username;
    
    @NotBlank(message = "密码不能为空")
    @Size(min = 6, max = 100, message = "密码长度6-100")
    private String password;
    
    @Email(message = "邮箱格式不正确")
    private String email;
    
    @Pattern(regexp = "^1[3-9]\\d{9}$", message = "手机号格式不正确")
    private String phone;
}
```

### 5.2 SQL 注入防护

**必须使用参数绑定**：

```xml
<!-- ✅ 正确：使用参数绑定 -->
<select id="findByUsername" resultType="User">
    SELECT * FROM sys_user WHERE username = #{username}
</select>

<!-- ❌ 错误：字符串拼接 -->
<select id="findByUsername" resultType="User">
    SELECT * FROM sys_user WHERE username = '${username}'
</select>
```

### 5.3 敏感信息处理

**禁止在代码中硬编码**：

1. 密码
2. API Key
3. 数据库密码
4. 加密密钥

**使用配置管理**：

```yaml
# application.yml
spring:
  datasource:
    password: ${DB_PASSWORD}  # 从环境变量读取
```

### 5.4 权限校验

**必须校验**：

1. 用户登录状态
2. Token 有效性
3. 项目访问权限
4. 操作权限
